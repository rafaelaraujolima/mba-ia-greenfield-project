### SI-03.5 — Worker de processamento de vídeo
- **Status:** complete
- **Tests:** `src/videos/video.processor.integration-spec.ts` (3 tests — real Redis/BullMQ queue+worker, real MinIO upload/download, real `ffmpeg` probe + thumbnail extraction against a synthetic `testsrc` fixture, real Postgres updates) — all passing
- **Observations:** Added `VideoProcessor` (`@Processor('video-processing')`, extends `WorkerHost`) and `src/main-worker.ts` (`NestFactory.createApplicationContext(AppModule)`, per `TD-03`). Registered `VideoProcessor` in `VideosModule` as the plan and TD-03 specify ("mesmo `VideosModule`") — but that means both `main.ts` (API) and `main-worker.ts` (worker) instantiate it, since both boot `AppModule`. To keep the API process from also consuming FFmpeg jobs (the exact thing TD-03's dedicated-container design exists to avoid), the `@Processor` is registered with `autorun: false`, and only `main-worker.ts` explicitly calls `videoProcessor.worker.run()` to start consuming — `main.ts` never touches it, so the API process holds an idle, non-consuming `Worker` instance. Added `start:worker`/`start:worker:dev`/`start:worker:prod` npm scripts mirroring `start`/`start:dev`/`start:prod` (via Nest CLI's `--entryFile main-worker`); left the `nestjs-worker` Compose service idling (no `command:` override), matching `nestjs-api`'s existing dev convention of manual `docker compose exec ... npm run start:worker:dev` rather than auto-starting — the plan's "atualizar o comando de start ... no Compose" reads as the eventual production wiring, and this project has no prod Dockerfile/compose overlay yet to wire it into. On failure, `@OnWorkerEvent('failed')` checks `job.attemptsMade >= job.opts.attempts` before marking `status=error` — mid-retry failures are logged but leave the video untouched, matching TD-06. Hit and fixed two real bugs while writing the integration test: (1) `Test.createTestingModule().compile()` alone never triggers `onApplicationBootstrap`, which is when `@nestjs/bullmq`'s `BullExplorer` actually constructs the underlying `Worker` — calling `.worker` before that throws; needed an explicit `await module.init()`, unlike the other Bull-touching integration specs (producer-only `@InjectQueue` usage apparently only needs `onModuleInit`, already covered by `.compile()`); (2) a `worker.once('completed'/'failed', ...)` listener in the test raced the framework's own un-awaited `@OnWorkerEvent` listener that persists the DB update, so the test could read the video row before the write landed — replaced with polling `videoRepository` until status leaves `processing`. `npx tsc --noEmit` clean; full suite 179/179 (unit+integration) + 63/63 (e2e) green; lint exits 0 with only pre-existing debt. Noted, not acted on: stale `video.process` jobs from earlier SI-03.4 test runs (enqueued back when no worker existed to consume them) surfaced as harmless "entity not found" error logs the first time this suite's worker drained the backlog — no assertion failures, and the test DB/Redis are dev-only shared state, not a production concern.
